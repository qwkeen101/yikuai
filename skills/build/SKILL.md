# 实现

先读 `${CLAUDE_PLUGIN_ROOT}/docs/flow-files.md`。用户在参数里指定了块或任务就做那个；没指定就取状态为「实现中」的块，有多个时问用户先做哪个。

## 步骤

1. **准备。** 读 blocks.md，确认这一块依赖的块都已「完成」；有没完成的，告诉用户要先做完哪一块，结束。读本块 spec.md、全部任务、data.md，以及项目 CLAUDE.md / AGENTS.md 里关于测试、提交、代码审查的规矩。找出项目的测试和类型检查命令。

   完成标准：知道哪些任务可做，要跑哪些命令。

2. **做一个任务。** 状态改为「进行中」。能先写测试的，先写一个会失败的测试，跑一下看它失败，再写实现让它通过；一次一个行为，直到验收标准全部满足。跑这个任务相关的测试和类型检查。

   完成标准：验收标准全部打勾，相关测试和类型检查通过。

3. **收一个任务。** 按项目规矩决定是否做代码审查。任务状态改为「完成」，blocks.md 当前步骤更新为「任务 K/N 完成」，提交，提交信息写上任务编号和标题。

   完成标准：任务已是完成状态，改动已提交。

4. **下一个。** 重新找可做的任务，回到第 2 步。几个可做的任务互不依赖、也不改同一批文件时，可以并行：各派一个子代理，各用独立的工作树或分支，做完再合回；其余串行。

   完成标准：没有可做的任务了。

5. **收尾。** 跑全量测试。全部任务完成且测试通过时，块状态改为「完成」，告诉用户下一个能设计的块和该运行的技能。还有任务卡住时，说明卡在哪、等什么。

   完成标准：blocks.md 和任务的实际情况一致。

## 实现中发现设计要改

- 只影响本块、还没实现的部分：直接改 data.md 或 spec.md，在 decisions.md「已定」记一行，接着做。
- 影响其它块、已完成的任务或用户确认过的界面：停下，告诉用户要改什么、为什么，等用户定。
