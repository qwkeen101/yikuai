# yikuai 状态文件约定

yikuai 的所有技能读写使用者仓库里的同一组文件。结论当场写进文件，新会话只靠这些文件接着做。

## 通用规则

- 仓库里还没有 `docs/flow/blocks.md` 时，告诉用户先运行 `/yikuai:setup`，然后结束（setup 自己除外，它负责建这个文件）。
- 每完成一步，就更新这一块在 blocks.md 里的「当前步骤」。
- 日期一律写 `YYYY-MM-DD`。
- `GLOSSARY.md` 和 `docs/adr/` 等到第一次有内容要写时再建。

## 目录

```text
docs/flow/
  blocks.md                 块清单
  parked.md                 待确认清单
  <NN-slug>/
    data.md                 数据结构（格式见 schema 技能的 DATA-FORMAT.md）
    decisions.md            未决问题和已定决定
    spec.md                 规格（格式见 spec 技能的 SPEC-FORMAT.md）
    tickets/NN-<slug>.md    任务
docs/design/<NN-slug>/      效果图
GLOSSARY.md                 术语表
docs/adr/NNNN-<slug>.md     架构决定记录
```

块目录名是 `NN-<slug>`：`NN` 是两位的设计顺序号，slug 用小写英文和短横线（如 `02-orders`）。中文块名写在 blocks.md 里。

## blocks.md

~~~markdown
# 块清单

任务存放：本地文件
现有结构：prisma/schema.prisma, src/types/

| 编号 | 名称 | 范围 | 依赖 | 界面 | 状态 | 当前步骤 |
|---|---|---|---|---|---|---|
| 01 | 账号 | 注册、登录、找回密码 | - | 有 | 实现中 | 任务 3/5 完成 |
| 02 | 订单 | 下单到取消的订单生命周期 | 01 | 有 | 追问 | 第 2 轮后，约剩 3 题 |
| 03 | 对账导出 | 按天导出订单对账表 | 02 | 无 | 待设计 | |

## 后续

- 优惠券：满减和折扣券（第二期）
~~~

- **任务存放**：`本地文件`，或 `GitHub Issues（owner/repo）`。由 setup 写入。
- **现有结构**：代码里定义数据结构的位置（迁移、模型、schema 文件、共享类型），由 setup 写入，schema 从这里开始盘点。
- 表格行序就是设计顺序。**范围**一句话；**依赖**写块编号，`-` 表示无；**界面**写有或无。
- **当前步骤**一句话说明在这个状态里做到哪，例如「等用户确认效果图」。
- **后续**放切块时超出本期的块。

### 状态

`待设计 → 定结构 → 看界面 → 追问 → 规格 → 实现中 → 完成`。界面为「无」的块从「定结构」直接进「追问」。

| 状态 | 该运行 | 什么时候进入 |
|---|---|---|
| 待设计 | `/yikuai:schema` | slice 写入 |
| 定结构 | `/yikuai:schema` | schema 开始处理这一块 |
| 看界面 | `/yikuai:mock` | data.md 经用户确认 |
| 追问 | `/yikuai:ask` | 效果图经用户确认（无界面的块：data.md 经用户确认） |
| 规格 | `/yikuai:spec` | decisions.md 的「未决」清空 |
| 实现中 | `/yikuai:build` | 规格和任务写好，任务清单经用户确认 |
| 完成 | 无 | 全部任务完成，全量测试通过 |

- **一次只设计一块**：处在「定结构 / 看界面 / 追问 / 规格」的块，同一时刻只有一个，它就是**当前块**。没有当前块时，下一个能开始设计的块是：排在最前、状态「待设计」、依赖的块都已「实现中」或「完成」的那一块。
- 一块能开始实现，要求它依赖的块都已「完成」。
- 用户要换一块设计时，原块保持状态，当前步骤写「暂停：<原因>」；暂停的块不算当前块。
- 状态只往前走。要退回（例如追问时发现结构要大改），先说明原因，用户同意后再改，并在 decisions.md「已定」记一行。

## parked.md

~~~markdown
# 待确认

| 编号 | 块 | 问题 | 暂按 | 记于 |
|---|---|---|---|---|
| P3 | 02 | 订单取消后库存是否立即释放 | 立即释放 | 2026-11-10 |

## 已处理

| 编号 | 块 | 问题 | 结论 | 处理于 |
|---|---|---|---|---|
| P1 | 01 | 手机号是否必须验证 | 按原推荐：必须 | 2026-11-12 |
~~~

- 编号 `P<n>` 全仓库递增，不复用。规格、任务里用编号引用它。
- **块**写块编号；不属于任何块的写 `-`。
- 处理后整行从「待确认」移到「已处理」，同时在所属块 decisions.md「已定」补一行。

## decisions.md

~~~markdown
# 02 订单：决定

## 未决

- 部分退款能否多次发起
- 未支付订单多久自动取消

## 已定

| 日期 | 问题 | 结论 | 理由 |
|---|---|---|---|
| 2026-11-10 | 取消订单是否要填原因 | 必填，5 个选项加「其他」 | 运营要按原因统计 |
| 2026-11-10 | 订单号格式 | 日期加 6 位序号 | 默认 |
~~~

- **未决**是这一块还要用户定的问题，一行一条。清空后这一块进入「规格」。
- **已定**一行一条。任何技能在这一块定下的事都追加到这里：schema 的复用取舍、mock 的改动、ask 的回答、build 里的小调整。按默认处理的小事，理由写「默认」。
- 搁置的问题只记在 parked.md，确认后再补进「已定」。

## 任务：本地文件

`docs/flow/<NN-slug>/tickets/NN-<slug>.md`，一个任务一个文件，编号按依赖顺序（被依赖的在前）。

~~~markdown
# 03 取消订单

状态：待做
依赖：01, 02

顾客在订单详情页取消未发货的订单，选择原因后订单变为「已取消」，占用的库存释放。

## 验收标准

- [ ] 未发货订单可以取消；已发货订单的取消按钮置灰
- [ ] 不选原因无法提交
- [ ] 取消后商品可售库存恢复
~~~

- **状态**：`待做`、`进行中`、`完成`。
- **依赖**：同一块内的任务编号，没有写 `无`。
- **可做的任务**：状态「待做」，并且依赖的任务都「完成」。

## 任务：GitHub Issues

blocks.md 写的是 GitHub Issues 时，用 `gh` 操作，一个任务一个 issue：

- 标题 `[NN-slug] 任务标题`，正文同上，去掉「状态」行。
- 依赖写在正文第一行：`依赖：#12, #13`。仓库支持原生的 blocked-by 关系时一并设上。
- 状态：open 且无人指派是待做；open 且已指派是进行中；closed 是完成。
- spec.md 的「任务」节按顺序列出每个 issue 的链接。

## GLOSSARY.md

~~~markdown
# 术语表

## 订单

**订单**：顾客一次结算产生的购买记录，包含商品、金额和收货信息。
_别用_：购买、交易

**取消原因**：顾客取消订单时选择的理由，用于统计。
~~~

- 只收这个项目特有的业务概念。表名、字段类型、通用编程概念放在 data.md 或代码里。
- 定义一两句，说它是什么。同一概念有多个叫法时选定一个，其余列在「别用」。
- 概念自然成组时用二级标题分组。

## docs/adr/

文件名 `NNNN-<slug>.md`，编号取已有最大值加一。三条同时成立才写：

1. **难以反悔**：之后改主意代价大。
2. **不看背景会奇怪**：以后的读者会问「为什么这样做」。
3. **确实有取舍**：有别的方案，因为具体理由选了这个。

正文一段即可：背景、决定、理由。被否掉的方案只在否掉的理由不显然时写。

~~~markdown
# 订单状态用单个字段加状态机

订单的待支付、已支付、已取消等状态不拆表，用 `status` 字段和 02 块 data.md 里的状态机表示。每个订单同一时刻只有一个状态，拆表会让每次查询都要联多张表。
~~~
